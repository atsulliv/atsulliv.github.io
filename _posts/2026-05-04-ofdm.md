## The System, at a Glance
So where are we working, anyway? An OFDM system is made up of a transmitter, the channel, and a receiver. The full Tx–Rx pipeline looks like this:

```
Tx -> QAM Mod -> IFFT -> Add CP -> Channel (speaker, wire, etc.) -> Remove CP -> FFT -> FEQ -> QAM Demod -> Rx Data
```

For this project, we are only working with the *receiver* end of our OFDM.

## Background

### What even is an OFDM?
Suppose you want to send something. That can be encoded in a string of bits, like 00 01 11 10 01 00 10 11. This can be mapped to a particular complex number, which we call the QAM symbol. (16 bits are mapped into 8 complex symbols.) Each of these symbols can correspond to an arbitrary number of subcarriers, to which we can define here to be 8.

The important insight is that QAM determines how many bits you encode per subcarrier, while OFDM determines how many subcarriers you transmit in parallel.

And then we take the IFFT: the IFFT is what allows all these independently modulated subcarriers to be combined into a single waveform and transmitted over some medium (cable, speaker, etc.)

On the receiving end of our OFDM, we need to first know that a signal has arrived. This is done through synchronization, which detects the start of the OFDM symbol. Now, after receiving the signal, we take the FFT, correct phase/angular distortions via an equalization process, map the constellations to the nearest constellation point, and then decode that into binary data to get our message.

### How Convolution Works
In my opinion, the best way to visualize convolution is the "flip and drag" method. 3Blue1Brown has a nice video on it, showing how a probability distribution is formed from two six-sided dice ([video, at 2:50](https://www.youtube.com/watch?v=KuXjwB4LzSA&t=170s)).

Likewise, the convolution operation is implemented in signal processing concepts. For example, a valid way to process a signal from input to output is to use a filter. Perhaps we want to filter it using a 4-tap filter, h[m], where for m in the range 0 to 3, h[m] is 1, and 0 everywhere else. We would compute the convolution by the following, given signal x[n]:

```
y[n] = Σ_m  h[m] · x[n − m]
```

Conceptually, what is happening is that, for a given n, we have h and x in the m-domain. x is flipped due to the negative sign, and shifted to the RIGHT if n is positive, and LEFT if n is negative. A clear way to see this is rewriting x as x[-(m-n)].

In code, we define a filter length, and utilize two loops and use block filtering. What is block filtering, you may ask? Suppose you have the following code:

```cpp
// FIR filter (outputs y[0], ..., y[filterLen - 2])
for (int n = 0; n < filterLen - 1; n++) {
    int32_t acc = 0;
    for (int m = 0; m < n + 1; m++) {
        acc += tempData[n - m] * coeff[m];                 // current block
    }
    for (int m = n + 1; m < filterLen ; m++) {
        acc += state[filterLen - 1 + n - m] * coeff[m];    // previous block
    }
    outputData[n] = acc >> 15;
}
```

**Why are there two blocks?**
So we call 512 samples at a time. In real-time DSP, we have to immediately produce an output, and we can't wait for the entire signal's convolution to be computed.

With a filter length of P:

```
y[n] = h[0]x[n] + h[1]x[n−1] + ... + h[P−1]x[n−(P−1)]
```

Each output needs the current sample plus the previous samples. Because of real-time computations, some of those P-1 samples are in the previous block during a previous poll, which means to accurately compute the convolution, we need both blocks (cur and prev).

`outputData` is assigned after `acc` is bit-shifted by 15, because the samples and coefficients are in Q15 notation.

A convolution will take 2 Q15 numbers and give a Q30 result. This is also why we use an int32 accumulator. But we truncate the 15 LSBs, which is fine because 15 precision points is still good.

Q15 is the fixed-point sign convention we use. The MSB is a sign bit, and the remaining bits are fractional representations. We can thus represent a number from -1 to +1 with 2^-15 bits' worth of precision.

### Cyclic Prefix, Overlap-Add (OLA), and Overlap-Save (OLS)
Why do we need a cyclic prefix?
Turning linear convolution into circular convolution, such that the convolution is performed seamlessly and efficiently. This relates to OLA and OLS methods because we prepend and append parts of the previous signal to convolve them.

### QAM and the Complex Plane
So why do we process these signals in the complex domain?

This is relatively simple. Recall that a signal can be represented in the following manner: A·e^(jθ), where we can easily represent the amplitude and phase of a sinusoidal signal simultaneously. This makes mathematical operations much easier, especially when working with the Fourier transform. How so? For example, we can simply represent this exponential using a single complex value: X = I + jQ.

When dealing with the IQ plane, the I is the component that is in-phase (Real), whereas the Q is the quadrature component (Im axis). Don't get confused with the jargon. It's just a representation of how much we can represent a particular signal with a given subcarrier frequency with a cosine wave (I) and a sine wave (Q), as they are orthogonal, and how strong that representation is (magnitude of IQ).

### DFT Optimizations
- DIF vs. DIT, splitting into N/2-point DFTs (radix-2)
- Precompute twiddle factors
- Avoid bit reversal: `y[n] = ifft( fft(x) .* fft(h) )`
- Scaling: avoid it if you can; otherwise, fix the scale per stage
- Buffer management

## The OFDM Receiver
The receiver has three jobs: find the symbol boundary, demodulate with the FFT, and design the FEQ. I implemented this as a finite state machine, with the frame structure **Sync Symbol → FEQ → Data 1 → Data 2 → ...**

### The FSM

#### 1. STATE_SYNC (Synchronization)
*How do we know when the signal has arrived?*

When the receiver starts listening, it continuously receives samples from its microphone or ADC. However, it doesn't know where the OFDM frame begins. To identify the beginning, the transmitter sends a known synchronization sequence, and we use an autocorrelation function that, once the output crosses a particular threshold, we know to move onto the next state. Else, continue staying in STATE_SYNC.

#### 2. STATE_FEQ_DESIGN
*How do we compensate for the distortion introduced by the channel?*

Even after identifying the beginning of the OFDM frame, we still don't know how the communication channel has affected our transmitted signal.
For example, when transmitting audio through a speaker and microphone, different frequencies may experience different amounts of attenuation and phase shift because the channel acts like a filter. To estimate this distortion, the transmitter sends a known training symbol. We remove its cyclic prefix and perform an FFT to recover its frequency-domain representation. Since we already know what was transmitted, we can compare the received values with the expected values to estimate the channel response:

```
Y[k] = H[k]·X[k] + W[k]
```

Ignoring noise for the initial estimate:

```
Ĥ[k] = Y[k] / X[k]
```

Here, `X[k]` is the known transmitted training symbol, `Y[k]` is the received symbol, and `H[k]` is the channel's frequency response.

We then calculate equalization coefficients:

```
G[k] = 1 / Ĥ[k]
```

These coefficients allow us to compensate for the amplitude and phase distortion on each subcarrier.

Once the equalizer coefficients have been calculated, we transition to STATE_DATA_DEMOD.

#### 3. STATE_DATA_DEMOD
*How do we recover the original transmitted bits?*

Now that we've established synchronization and estimated the channel, we can decode the actual data symbols.

For each received OFDM symbol, we:


1. Perform an FFT to separate the individual subcarriers.
2. Apply frequency-domain equalization using the coefficients calculated in STATE_FEQ_DESIGN.
3. Perform QAM demodulation by finding the nearest valid constellation point for each data subcarrier.
4. Convert those constellation points back into their corresponding binary values.

Mathematically, the equalization operation is:

```
X̂[k] = G[k]·Y[k]
```

Ideally, this produces complex values close to the original QAM constellation points.

Because of noise and imperfect channel estimation, the recovered values won't necessarily fall exactly on the constellation points. We therefore choose the nearest valid point to determine which bits were transmitted.

If our packet contains multiple data symbols, we continue processing them using the same estimated channel response. Once the entire packet has been decoded, the FSM returns to STATE_SYNC to search for the next transmission.

### Working with Apple's Accelerate Framework
The iOS Accelerate framework's vDSP module has its own complex data types. Its split-complex format stores real and imaginary parts in separate arrays (stride 1):

```c

    float *imagp;
```
